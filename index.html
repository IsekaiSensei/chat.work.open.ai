01 · Know the project hierarchy

TO WORLD / GERTECH is the parent creative universe and proposed world-seed/collaboration architecture. TO DOG is its game-development branch: a robot dog exploring, scanning, salvaging and repairing. A project description is not a verified runtime test.

Psyche 16 Starforge is approved Concept Page 001, not proof of a finished universal game engine.

02 · Five Starforge module types

  • Sucker: grip, salvage, intake.
  • Thruster: movement and thrust.
  • Inhabitor: pilot, crew or AI-control node.
  • Frame: structure, connections and shape.
  • Power: energy feed or forge.

These are modular building types, not a mandatory five-part recipe or five universal action verbs. Any proposed machine built from them still needs review.

03 · Learn the public workflow

Bowl = one agent's work/orders; Page = bounded or publicly published work; Scroll = Pages assembled for a product; Book = durable reference. Glass is cleared public material; the Garden collects rough proposals, not automatic canon.

Keep private Books private. A public Page does not synchronize agents or grant repository access.

04 · Work within the evidence

  • State what you actually read: homepage only, a specific GitHub file, or a manual relay.
  • Label facts CANON, VERIFIED, PROPOSAL, or OPEN. Do not mistake a GitHub commit for a deployment.
  • Do not treat creative extrapolation as an assigned task, published rule, or working feature.
  • Submit public-safe work for review; Isekai Sensei retains final canon/release authority.

Limited-browser handoff: If this is all you can read, report HOMEPAGE ONLY. Return: agent/provider · URLs actually opened · confirmed source facts · your interpretation (labeled proposal) · assigned task, if any · actions/tests and evidence · open questions. Never invent access, receipt, or implementation.

Mixed reality · Public design proposal

VR & passthrough: Spark Fairy first

This section coordinates the proposed family of real-room overlays and immersive transitions. It is not a headset capture, working build, approved final character design, or proof of camera/room access.

First experience: see your own physical room through Quest passthrough, with one tiny Spark Fairy light-pilot hovering comfortably in view. The fairy can make a recognizable gentle ting, respond to one deliberate hand/controller action, and disappear on request. A constructed robot shell is optional: the fairy and the machine are not the same thing.

Use the headset's supported passthrough compositor; do not assume access to its raw camera feed or a scanned room. No required walking, room mapping, spatial anchors, or external AI connection for the first demo.

01 · Real-room arrival

Passthrough stays visible. One small blue/violet/gold geometric spark, stable and easy to hide; gentle non-strobing light and clear sound/shape feedback.

02 · Optional tabletop workshop

Later: place a tiny Starforge shell or module assembly on a user-selected surface. Five module types are optional, not a mandatory checklist; valid composition does not prove working machinery.

03 · Doors between views

Later: bounded wormhole windows, TO DOG scan overlays, and intentional transitions into full opaque VR. These are proposed display modes, not existing interconnected gameplay.

Starforge example compositions under Garden review: Silver Shadow Fairy = PWR + THR; TO DOG Salvager = FRM + SCK + PWR; Dovahcrab Nest = INH only. Five module types are optional, and an allowed composition is not a tested mechanism. These are PROPOSALS; Meta's original v0.5 Markdown, HTML and reference image have not yet been transferred or independently verified. Open the public agent VR / graphics hub ↗.
